**Trigger:** An implementer or acceptance reviewer reads “Native tests ... all120 camera/replay values ... Check applicable final channels against CPU reference” as a mandatory full-resolution GPU-versus-CPU comparison for every one of the 120 values in every required row/lane/pass. That is a natural reading of the candidate, reinforced by the gap report's explicit final-sample indices 0…119 plus 120.

**Consequence:** A D1-only observation-policy amendment silently enlarges the inherited acceptance workload. Conversely, an implementer following only the approved parent cannot tell whether their bounded native parity matrix is now insufficient. The report's claims cannot supply authority for that expansion.

**Requirement/proof:** Parent section 9 item 1 explicitly places “all120 camera values and first/last/wrap indices” under **CPU moves**. Item 2 separately requires independent CPU rays/geometry/IDs/material/RGB/intensity for asymmetric and dynamic, real Go2 fixture validation, and existing parity tolerances. Item 4 requires all six R0 and two R1 rows in both lanes, profiles, shadow/diagnostic variants, terminal-event rules and generation sentinel reset. The distinction is real; exhaustive camera-value/selection coverage is not equivalent to exhaustive full-resolution numerical GPU/CPU coverage. Neither a review summary nor this reviewer may turn one into the other.

**Why existing checks do not settle it:** The archived gap report is a Request changes assessment, not an accepted requirements amendment. CPU camera tests and a two-sample worker smoke prove neither exhaustive native output coverage nor its necessity. Candidate wording supplies no separate coverage map distinguishing camera values, replay selection, generation transitions and numerical output comparisons.

Preserve all120 CPU camera-value checks and the actual parent-required ABI/replay/first/last/wrap and native row/profile/diagnostic/sentinel coverage. State explicitly that this supplement does not introduce a mandatory all120 full-resolution numerical GPU/CPU comparison. Give a bounded case-to-requirement map for the native numerical cases using the existing oracle and tolerances; do not invent a new sample count, lower existing parity obligations, or treat this report as approval for reduced image resolution. ### F2 — P2: the new request deadline lacks a defined successful completion/retirement and expiry-race contract

**Location:** candidate lines 122–141 and 182–188. Integration sites: tests/support/guarded_custody_process.py:315–397 (`_native_worker_requests` / `exchange`) and :475–565 (the original core-owning supervisor loop). Existing core semantics: optical_worker/wait_supervision.py:133–135, :186–218, :328–335 and :470–493.

**Trigger/counterexample schedule:**

1. The client publishes a deadline D for EXECUTE sequence q and sends q.
2. The supervisor is briefly descheduled while the worker/getter runs past D.
3. The getter returns; the client receives an otherwise valid response, clears the shared deadline or replaces it with the next request's deadline.
4. The supervisor resumes and sees no expired q obligation.

The opposite incomplete implementation—never retiring the deadline—terminates a healthy worker after q has already succeeded. A stale response/client-finally clearing a newer request has the same identity problem. These are races in the proposed client/supervisor handoff, not alleged existing product code defects.

**Consequence:** The intended nonrenewable bound can be lost, or successful requests can cause false termination. The design settles creation and the blocked-forever case, but leaves the success/retirement transition, equality rule, and competing completion/expiry transition unspecified. Those are part of the new observation policy's lifetime, not incidental variable naming.

**Why the existing core/tests do not close it:** GuardSupervisorCore already rejects normal protocol success at or after its own active deadline (lines 133–135) and retains earlier deadlines on terminal entry. The proposed EXECUTE deadline is external to that core while the guard is IDLE. The original fixed client has only one harness deadline, records errors in an outcome dictionary and shuts down its command write side; the loop currently neither consumes a per-request deadline nor arbitrates its completion. A permanently blocked getter test cannot exercise late successful response retirement. The CPU probe confirms the existing core's behavior, not this absent bridge.

**Requested repair:** Freeze a small sequence-bound request-observation record in the existing client/supervisor, not a new service or product guard role. Specify: publication before send; exact worker/session and request sequence; the event that constitutes complete successful response observation; who commits retirement; monotonic-time comparison before success retirement; expiry wins at equality; partial/error/EOF/send failure enters the existing terminal path; late/stale completion cannot clear or replace an expired/current obligation; no next request until the preceding observation has an unambiguous successful retirement; terminal state permanently disables further requests. The core-owning supervisor thread remains the only caller that commits core fault/termination. A short nonblocking handoff can implement this; the shared lock/record must not be held across socket I/O, artifact writes or a blocking wait. Preserve any earlier core/ACK/emergency deadline. Require the command endpoint to be shut down/closed in a way that interrupts the client and prevents further sends before terminal evidence is published.

The exact representation is an implementation choice. The transition and deadline ordering above are the missing design contract. Using the existing operation timeout and process_observation_failed reason is otherwise appropriate.

**Closure proof:** CPU scheduling tests for success strictly before D, completion exactly at D and after D while the supervisor is delayed, stale completion of q after another sequence is considered, partial reply/EOF/send failure, and failure during transport closure. Later original-supervisor OS tests must still block before/inside/after enqueue/finish and in resolve, then prove actual worker exit/reap and joined client, without using the outer harness timeout as acceptance. Tests must show no target sync and no fabricated worker guard fact for an observer timeout.
