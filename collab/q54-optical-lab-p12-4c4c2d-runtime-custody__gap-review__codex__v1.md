## Findings

### F1 — High: the frozen failure grammar and unchanged component parsers exclude real producer histories

Locations: candidate lines 122–127, 206–211, 225–231; `native_bootstrap.py` `_ExternalSourceLoader.exec_module` (approximately 600–616), `complete_native_call` (1178–1194), `fail_native_call` (1063–1075), `_native_global_observations` (1220–1247), `replacement_observations` (925–947); `runtime_environment.py` native-global/replacement admitted-event checks (approximately 530–536 and 655–662).

Trigger A: delegated exec returns; normal wrapper checks pass; `complete_native_call(frame)` commits `completed`; the subsequent external `record("completed", ...)` or its new aggregate observer raises. The loader's actual except branch calls `fail_native_call(frame)`, which changes that completed frame to failed. The candidate permits only `started -> returned -> completed` and `started/returned -> failed`, and also requires journal final states to equal the component call ledger. It cannot satisfy both rules for this real boundary.

Trigger B: `complete_replacement` appends its admitted component event before the final file-call completion mutation; native-global admission similarly appends each admitted event before `_native_call_state(..., "completed", ...)`. An aggregate append/record failure after that component append, or another fallible check in this interval, leaves a real admitted event with a failed call. The existing strict parsers reject such a record. Production explicitly skips those strict validators when exporting failed component observations; the replacement exporter even comments that failure may interrupt the admission/call-completion commit. The proposed aggregate says it delegates all components to the existing strict parsers without defining an exception-free atomic commit or a bounded failed-prefix representation.

Consequence: an implementation must invent policy: erase an actual component tail, falsify a completed call, quietly change a previously approved parser/producer contract, or fall back to an older snapshot. Keeping an older durable snapshot is safe and useful for I/O failure, but it does not by itself close the promised positive failed-cut/observer-exception behavior or define whether the latest intact failed journal is representable. The conflict is especially relevant because this change adds fallible recording at precisely these mutation sites.

Evidence: the scratch CPU probe executes the actual production `fail_native_call` with a synthetic completed frame and observes `failed`. Separately, prefixes constructed from real successful Go2 component records, retaining admission then failing that call and its ancestors, are rejected with `invalid native global admission` and `replacement admission differs from observation`. These are explicit synthetic counterexamples to the proposed composition, not claims that the historical successful run failed. The original untouched component records pass their strict parsers. Source inspection proves the producer ordering that makes the prefixes relevant.

Repair direction: freeze the distinction between delegated return, local admission, final call completion and subsequent wrapper/observer failure. Choose and document a minimal compatible failed-prefix rule or an explicit whole-observation commit boundary, including what is retained when only part of that boundary commits. Do not erase previously observed success or turn later wrapper failure into native success. Specify completed-to-failed handling and how component parser compatibility is preserved/versioned. Also define partial external-admission construction: the object is retained before `__init__`, and initialization can fail before component fields exist; “null only before its producer exists” needs a precise initialized/available condition.

Proof required: actual loader/finder CPU tests fault immediately before and after each pending/admitted/component append, after call completion but before external completion append, and during aggregate append. Each test checks exact retained history, one sticky failure, accepted truthful partial record or explicitly selected older cut, no fabricated completion, no new ARM/COMPLETE/sync and no ordinary release. Include a swallowed nested failure followed by parent return. Retain and parse each chosen record with the final versioned rules.

### F2 — High: independent component tokens have no frozen join to aggregate identities or return/adoption facts

Locations: candidate lines 46–51, 76–79, 92–99, 122–131, 206–213; `native_bootstrap.py` `_replacement_token` (695–700), native-global token issuance (1165–1169), interpreter-alias event issuance (2692–2695), file create/return (550–566).

Trigger: produce a normal Go2 aggregate containing all three existing unchanged component payloads plus the new monotonically allocated global object table. The existing token namespaces are independent. In the actual checked record, native-global token 1 is `cython_runtime`; replacement `original` 1 is the original `torch._VF`, replacement token 2 is its exposed wrapper, class token 3 is its class; interpreter-alias main token 1 and publisher token 2 denote entirely different objects. The component journal entries contain only `event_index`. Neither the top-level objects rows nor those entries include a component-local-token to aggregate-object-token relation.

Consequence: interpreting component integers as aggregate integers contradicts actual producer identity, while interpreting them as local integers leaves no data with which replay can join the replacement original to its executed file module, the native value/root to the actual native module, the alias main/publisher to source custody, or component owners to guardian rows. Component transplantation/owner mutation tests cannot test those joins because the relation is absent. This is not a claim that public hashes should detect an entirely fabricated, self-consistent history; the issue is a missing consistency edge within a single supplied record.

The same absence is visible on the constructor/return failure path. A file-created object is held in `admission.records` before `return_native_call`, then explicit adoption can fail before the external `created` event. `file_call`'s returned details contain no object token. An objects row with a `first_journal_index` and null guardian sequence cannot say which returned call produced or retained that object unless the producer/consumer association is specified. Merely promising that returned-before-adopt objects may have null guardian sequences does not encode that association. Runtime binding/stream construction failures similarly need an explicit decision about which available returned identities are described and how, without pretending success.

Repair direction: freeze a minimal occurrence-bound mapping emitted from held exact identities, preserving existing component payloads if desired. Identify the namespace and local token, global token and the occurrence at which that relation becomes available. Alternatively define versioned component projections that use the common allocator, accounting for fixed interpreter-alias tokens and existing validators. Define how file return tokens and failed pre-adoption holds enter the journal/object table. Freeze token uniqueness, first-use/index rules, nullable adoption semantics, permissible multiple names for the same object, and cross-checks against the relevant guardian adoption roles/scope at the cut. No extra native inspection or authority registry is needed.

Proof required: live issuer tests show the same held object receives one aggregate token across file/creator-self/replacement/native-root/alias views; distinct objects with the same component-local integer stay distinct. Mutate only a replacement-original/global-root/alias mapping or returned-call token and require rejection. Inject adoption failure after module/stream return, preserve exact sentinels through terminal disposition, and demonstrate an honest partial record without inventing a success/adoption event. Parsed copies still confer no live authority.

### F3 — High: source/interpreter cross-binding has no specified trusted comparison input

Locations: candidate lines 69, 86–90, 212–213, 236–242; `native_sources.py` `NativeRepositorySourceSnapshot.sha256` (201–210); `native_bootstrap.py` `_capture_interpreter_alias`, `_INTERPRETER_ALIAS_CUSTODY`, `interpreter_alias_observations`; `runtime_environment.py` `validate_interpreter_alias_observations` (554–598).

Trigger: retain the legitimate alias shape, resolution, event, executable and version, but substitute a different 64-hex `source_sha256`. The unchanged component parser accepts it, as intended for its local descriptive role. The candidate promises comparison with the “actual frozen source snapshot/interpreter launch,” but names only a separately supplied `RuntimeEnvironmentContract` and a `(runtime_record, environment, custody_artifact)` attachment interface. The aggregate has three source strings, not an independently supplied source descriptor; lifecycle/custody have configuration/lane/guard history but no source/stdlib identity. The source snapshot's digest covers repository revision/lane/catalog/policy/repository sources and does not cover multiprocessing source bytes or the alias interpreter descriptor. The environment has interpreter executable/hash/version but does not contain the complete captured alias source/stdlib topology descriptor.

Consequence: an implementer cannot compare all promised facts using the frozen inputs. It could only trust the record's own hash-shaped claims, hard-code a deployment source hash, add an undocumented argument/side channel, or discover/read filesystem state during parsing. The last two contradict the claimed frozen CPU-only schema boundary; hard-coding a second deployment authority is unnecessary.

Evidence: the actual Go2 alias payload passes unchanged; changing only its source SHA256 to 64 zeroes also passes the existing alias parser in the read-only CPU probe. This is expected component behavior and is not reported as a component bug. The aggregate is expressly supposed to supply the missing upstream comparison, but its input contract does not contain it.

Repair direction: specify the already-trusted launch/source snapshot and captured interpreter-alias descriptor supplied to the aggregate validator, with their exact fields and producer timing, including early cuts before environment binding. State precisely which environment interpreter fields match that descriptor, which source revision/catalog/snapshot claims are compared, and how those expected facts are retained/exported independently of the downstream runtime record. This remains a one-way upstream reference and does not require a new authority or cyclic hash. If a check is intentionally producer-only rather than offline replay-verifiable, narrow that promise explicitly and describe the evidence consumer's trust boundary.

Proof required: alias-source digest/path/ABI/version/topology and source revision/catalog/snapshot substitutions fail against unchanged trusted launch inputs; two legitimate launches each pass their own inputs but cross-attachment fails. Early environment-null records have a defined validation mode, and no parser imports a backend, discovers a runtime, reads arbitrary paths or mints live authority.

## Checked design strengths and non-blocking clarifications

1. The aggregate is correctly downstream and descriptive. Delegating lifecycle replay/terminal disposition to `GuardedLifecycleEvidence` and `validate_custody_artifact`, keeping custody artifacts unchanged, and prohibiting source/manifest back-references avoids duplicated lifecycle authority and cyclic hashing. Retention by the adopted source session is feasible. Existing terminal evidence distinguishes guardian-table release from destruction of every native owner/cache; the candidate preserves that distinction.
2. Storage projection is feasible without another GPU getter loop. `register_prepared_native_input` retains exact array references, frozen `_PhysicalStorageSignature` instances, storage-owner references and the ready event in `_PREPARED_STORAGE`; `assert_prepared_storage_registered` already performs the untimed physical recheck. Project only those stored entries after that check. Freeze the CPU projection API and parser field domains/ranges, manifest name/shape/extent checks, CUDA versus Warp stride units, zero-sized storage behavior, and readiness-event/source identity joins in the revised schema/tests. Do not call `_physical_storage_signature` again solely for evidence or use the readiness assertion as a shortcut. Independently checked additional feasibility detail: `NativeArrayManifest`/`NativeInputManifest` live in `native_input.py` (113–191), which imports NumPy at line 12 and materializer modules at import time; there is no `from_payload` manifest parser. Therefore the existing payload is serializable CPU data, not an existing safe parser the aggregate can import. The revised delivery boundary should explicitly extract/share the inert manifest layout/codec/validation into a dependency-free module, preserving existing payload bytes and public imports, or state another single-source arrangement. It must not copy an independently drifting manifest schema into runtime_custody or import native_input during early/failure replay. Freeze the allowed nested `semantics` shape for this canonical-source path and content/topology consistency checks, with CPU import-closure and unchanged-manifest-digest evidence. This is an implementation-boundary clarification supporting the proposed architecture, not a claim that the current dataclasses are an already strict parser.
3. The specified external kinds match actual normal diagnostics: creator-self checks are three distinct absence checkpoints; expected absent probes have real active requester context; disabled denials/fallbacks are separate from executable imports; namespaces have no file/delegated-body provenance; Triton can remain resolution-only. The final replay table should list exact ordering around `file_call returned` and external `created/completed`: create emits `created` before call completion; exec completes its call before emitting external `completed`; ordinary creator publications occur after delegated return during wrapper reconciliation. Do not conflate an active file-wrapper interval with a still-running delegated exec.
4. Checkpoint-only persistence may leave a killed worker's last durable record at the previous phase, before the in-flight call began. That is an honest prefix, not evidence that the worker did no later work. Keep this limitation explicit; do not manufacture a started-call row after death. Atomic writer failure must retain the earlier complete file, and collector/parse failure must enter existing sticky failure without retry/ARM/sync. These decisions are appropriate; the valid-cut rules in F1 must make them executable.
